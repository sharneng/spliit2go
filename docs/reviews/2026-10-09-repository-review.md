## Outcome and scope

The README describes most shipped features accurately. The decision records contain useful historical reasoning, and the privacy policy distinguishes Android ML Kit from iPhone Vision correctly. Documentation maintenance has lagged behind several feature changes, particularly receipts, group rows, default splits, navigation, and sync lifecycle.

The more important findings are implementation gaps behind documented guarantees: server identity is not part of group/expense keys, a stale refresh can delete a newly synced row, ambiguous create failures can duplicate expenses, and date-only values are persisted as timezone-dependent instants.

## Correctness and architecture findings

### F1 — P1: Scope local identity by server before joining duplicate remote IDs

References: [lib/db/app_database.dart:100](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/db/app_database.dart#L100), [lib/db/app_database.dart:295](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/db/app_database.dart#L295), [lib/screens/join_group_screen.dart:220](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/join_group_screen.dart#L220), [lib/sync/outbox.dart:102](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/sync/outbox.dart#L102).

`Groups` and `Expenses` use the remote `id` alone as their primary key. Expenses, attachments, active-user/default-split state, outbox queues and receipt jobs are addressed by these unscoped IDs. `cacheJoinedGroup` upserts a group and later records its server URL; joining the same ID from another server overwrites the existing group. Pending expenses survive the snapshot replacement and are then sent using the new server URL.

This is realistic for a self-hosted server cloned or restored from another instance; it does not require a random ID collision. The reproduction joins `same-group` on A, queues an A expense, joins `same-group` on B, then shows that the expense is POSTed to B. The two joined groups also collapse into one. Independent expense-ID collisions can cause cache/primary-key conflicts even when group IDs differ.

Introduce a local joined-group key, with a unique constraint on `(canonicalServerUrl, remoteGroupId)`. Scope remote expense identity by that joined group, and carry the local key through settings, navigation, outbox, receipt references and downloader status. Keep the remote ID only for API calls. Categories already demonstrate server-scoped identity. Add migration and cloned-server tests; do not solve this by silently refusing or moving existing pending rows.

Documentation affected: README “groups on different instances can coexist,” store listing, multi-group design. These need the identity invariant and migration described once implemented.

### F2 — P1: Invalidate pre-create snapshots when a pending row becomes synced

References: [lib/db/app_database.dart:579](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/db/app_database.dart#L579), [lib/db/app_database.dart:718](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/db/app_database.dart#L718), [lib/db/app_database.dart:743](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/db/app_database.dart#L743), [lib/screens/group_screen.dart:187](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/group_screen.dart#L187).

The generation guard protects edits/deletes, but `markSynced` never advances it. A refresh can read its generation and receive a server snapshot before a create commits, then apply that snapshot after `markSynced` changes the pending row to a normal row. `replaceServerExpenses` deletes non-pending rows and inserts the old snapshot, so the newly synced expense disappears from the cache. Associated receipt references can also be pruned. The expense still exists on the server and may return on another successful refresh, but balances, details and offline views become wrong in between.

The reproduction saves a pending expense, captures the generation, marks it synced, then applies an empty snapshot at that generation: the write is accepted and the row is gone. `GroupScreen` starts a refresh and independently listens for connectivity sync, so this interleaving is available in the UI. Multiple refreshes at one generation can also finish out of order; there is no request sequencing.

Advance the mutation generation when acknowledging a create, including the no-parsed-server-ID path, and serialize or supersede refreshes per joined group. Put this policy in a repository/sync service shared by GroupScreen and BalancesScreen. Test delayed pre-create snapshots, concurrent refresh completion, edit/delete races, and receipt retention. A database watch stream does not itself prevent stale network writes.

Documentation affected: README sync explanation and `GroupScreen._syncThenRefresh` comment, which currently asserts there is no race.

### F3 — P1: A successful server create with a lost response is replayed

References: [lib/sync/outbox.dart:102](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/sync/outbox.dart#L102), [lib/sync/outbox.dart:122](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/sync/outbox.dart#L122), [lib/api/spliit_client.dart:475](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/api/spliit_client.dart#L475), [docs/decisions/receipts.md:56](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/docs/decisions/receipts.md#L56).

The outbox submits a server-generated-ID create, then acknowledges it locally. If the server commits but the response is lost, the row stays pending and a subsequent flush creates another expense. A process exit or local database failure between remote commit and local acknowledgement has the same uncertainty. Per-group serialization prevents overlapping in-process flushes; it does not provide idempotency across retries.

The reproduction's fake server commits on its first request and throws a transport error instead of returning the response. Two flushes produce two accepted creates. This is particularly significant for settlements, which change the debt twice.

Document the actual delivery semantics and distinguish definite rejection from an **unknown create outcome**. The strongest fix is an upstream-supported idempotency key persisted with the local operation. Without such a contract, define a reconciliation/user-verification flow for ambiguous creates before blindly repeating them; content matching alone cannot prove that two identical expenses are duplicates. Apply the same reasoning to group creation. Do not promise exactly-once delivery from a client-side mutex.

The receipt decision's assertion that duplicating the expense is unacceptable needs an explicit account of this unresolved failure window. Its existing explanation that acknowledged creates are not replayed remains valid.

### F4 — P2: Preserve calendar dates independently of device timezone

References: [lib/db/app_database.dart:38](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/db/app_database.dart#L38), [lib/db/app_database.dart:1023](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/db/app_database.dart#L1023), [lib/services/date_only.dart:42](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/services/date_only.dart#L42), [docs/decisions/date-handling.md:50](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/docs/decisions/date-handling.md#L50).

API conversion correctly rebuilds a local midnight from the wire date. SQLite then stores that `DateTime` as an epoch value and reconstructs a local `DateTime` when reading it. After a timezone change, the same epoch can fall on a different calendar day. For example, October 9 midnight in New York reads as October 8 at 21:00 in Los Angeles. A travel expense cached before flying west displays on the previous day; an unsynced expense can send that changed date to the server.

The reproduction persists the exact epoch of New York midnight and reads it in a Los Angeles test process. This simulates the persisted-value portion of a timezone change, not a live device timezone switch.

Use a calendar-date value and explicit SQLite representation such as `YYYY-MM-DD` or an integer date encoding. Keep `createdAt`, activity times and last-opened times as instants. Plan the migration carefully: existing epoch values do not retain the timezone in which a pending calendar date was chosen. Server-backed dates can be refreshed; recovering pending dates perfectly requires information the old schema lacks.

The date decision and a test comment also incorrectly call Drift's default storage “epoch millis”; it is second-granularity here, as the multi-group decision already explains. Correcting that terminology alone will not fix timezone dependence.

### F5 — P2: Automatic expense sync belongs to the application lifecycle

References: [lib/screens/group_screen.dart:130](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/group_screen.dart#L130), [lib/screens/group_screen.dart:138](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/group_screen.dart#L138), [lib/screens/group_screen.dart:160](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/group_screen.dart#L160), [lib/screens/group_screen.dart:442](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/group_screen.dart#L442), [lib/main.dart:263](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/main.dart#L263).

The expense connectivity listener belongs to a mounted `GroupScreen` and flushes only that screen's outbox. On the group list, or while another group is open, reconnecting does not flush pending expenses for a closed group. Startup calls `_refresh`, not an explicit flush; successful initial sync therefore depends on the platform delivering a connectivity event. Pull-to-refresh calls `_refresh` and only reads, despite the nearby comment saying it is a sync fallback.

These are source-inspection findings; the five saved reproductions do not include a widget lifecycle test. The README and store listing currently promise automatic reconnect sync without describing this screen constraint.

An app-scoped foreground coordinator should enumerate joined groups with pending work and flush them on startup, resume and reconnect, with per-group serialization and server-specific clients. Give manual refresh a defined sync-and-refresh behavior. This recommendation does not require operating-system background execution; document whether sync requires the app to be open, and handle that foreground lifecycle reliably.

### F6 — P2: Bound API requests and reject non-progressing pagination

References: [lib/api/spliit_client.dart:144](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/api/spliit_client.dart#L144), [lib/api/spliit_client.dart:181](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/api/spliit_client.dart#L181), [lib/sync/outbox.dart:102](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/sync/outbox.dart#L102).

Most tRPC GET/POST requests have no application deadline. A hanging create blocks the serialized outbox for that group; reads leave loading/saving operations waiting indefinitely. Receipt upload/download paths have deadlines, so the policy is inconsistent.

`fetchExpenses` continues whenever `hasMore` is true without checking that `nextCursor` exists or has not already been visited. A missing cursor repeats the first page; a repeated cursor repeats another page, potentially allocating an unbounded list. The reproduction returns the same cursor and stops the fake server after four requests; requests two through four are identical. Activity pagination already contains a progress check, but expense pagination does not.

Centralize transport deadlines and error conversion. Track visited opaque cursors and reject missing/repeated cursors when more pages are claimed; avoid assuming all cursors are numeric. Add deadline, malformed-page and cancellation tests. Classify a timed-out mutation under F3's uncertain-outcome policy rather than treating it as proof the server did nothing.

### F7 — P2: A global error snackbar does not recover failed local operations

References: [lib/main.dart:263](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/main.dart#L263), [lib/screens/group_list_screen.dart:137](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/group_list_screen.dart#L137), [lib/screens/expense_details_sheet.dart:560](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/expense_details_sheet.dart#L560), [lib/screens/expense_details_sheet.dart:591](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/screens/expense_details_sheet.dart#L591).

Startup's database migration/read is outside the initial-link catch; if it fails, `_checked` never becomes true. Group-list loading similarly has no local failure/retry state. Failed-expense Retry/Discard sets `_busy` and awaits database writes without local catch/finally recovery. A failed write can leave actions disabled even though the global handler shows diagnostics.

This is a code-path audit, not a reproduced disk-failure scenario. Add recoverable operation state at the ownership boundary: startup/list error views with retry, and catch/finally around pending-expense actions. Inject migration/read/write failures in focused tests. Keep the shared error-classification policy, but separate reporting an error from restoring the operation's usable state.

### F8 — P2: Receipt “storage limit” and usage describe different totals

References: [lib/services/receipt_cache.dart:130](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/services/receipt_cache.dart#L130), [lib/services/receipt_cache.dart:177](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/services/receipt_cache.dart#L177), [lib/services/receipt_cache.dart:209](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/services/receipt_cache.dart#L209), [lib/services/receipt_cache.dart:226](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/lib/services/receipt_cache.dart#L226), [docs/privacy.md:20](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/docs/privacy.md#L20), [docs/privacy.md:58](https://github.com/sharneng/spliit2go/blob/062deeb16ccd59a7e13e43be43e08bbdd1f18d96/docs/privacy.md#L58).

Eviction accounts for stored files plus pending attachment bytes, but `usage()` reports only stored files. Pending originals are intentionally protected, `storePending` performs no capacity check, and `store` keeps the newly viewed/captured receipt even if eviction cannot bring the total under the configured limit. Thus the setting is an eviction/download budget, not a hard cap, and the displayed usage can omit the bytes preventing a favorite download.

The receipt decision acknowledges that the size display and Clear exclude pending originals, but the public privacy policy says copies stay within the configured limit and are removed as needed to stay under it. That guarantee also fails for a large currently viewed receipt.

Prefer preserving pending originals, but name the budget accurately and show stored copies and pending originals separately, with their total. Explain that protected originals/captures or the current receipt can exceed the budget, and that Clear preserves unsent originals. Add storage-policy tests for an oversized viewed receipt and protected originals exceeding the budget.

## Refactoring and structure opportunities

These are incremental opportunities, not a recommendation for a framework migration or wholesale rewrite.

1. **Give the application ownership of clients and jobs.** SpliitClient and ReceiptCache allocate HTTP clients without an explicit disposal contract; route construction repeatedly creates clients, while AppRoot disposes the database. Define owned versus injected clients, reuse by server, stop/await app jobs before database shutdown, and close owned resources. ReceiptDownloader already closes its per-run client; extend that clear ownership discipline to other services. This supports F1/F5/F6.
2. **Extract a group/expense repository boundary.** Move `cacheJoinedGroup` out of JoinGroupScreen: GroupSettingsScreen imports the join screen for persistence, while the join screen imports group settings. Route construction is duplicated in AppRoot and GroupListScreen. Centralize joined-group caching, mutations, refresh sequencing and outbox triggers; let screens manage presentation/navigation. Also move API exception definitions into a small protocol/errors module to remove the SpliitClient ↔ ErrorReporter import cycle.
3. **Separate expense form state from widgets.** ExpenseScreen is roughly 1,650 lines covering draft construction, validation, split math, defaults, receipts, OCR and persistence. Extract a draft/controller with pure validation/serialization, a repository save operation, and form sections. Preserve the existing pure share/receipt helpers and integration tests; do not mirror every widget method in a new abstraction. Dispose the title and amount TextEditingControllers as well as the controllers currently disposed at line 472.
4. **Keep database schema/migrations apart from query/policy growth.** AppDatabase mixes six tables, migrations through schema 17, receipt pruning, outbox transitions and group settings in one roughly 1,250-line file. Separate table definitions and cohesive query modules/DAOs where useful, while preserving transaction boundaries. Start with scoped identity/calendar-date migrations and sync acknowledgement; file splitting alone would not address the actual problems.
5. **Project group-list summaries in SQL.** `_load` sequentially loads/sorts every expense for every joined group just to calculate first/last dates. Return group summaries with MIN/MAX date projections and participant counts, and consider indexes on the frequently filtered group/expense-reference columns. Measure larger histories before adding broad indexing or aggregation caches. Guard overlapping list loads from applying an older result. This is a scaling opportunity, not a measured performance regression.
6. **Use one strict wire mapper for financially meaningful fields.** List/get duplicate expense decoding. Unknown split modes become “evenly,” unknown recurrence becomes “none,” and missing IDs can become the literal string `null`. These defaults can make an incompatible response look valid and change its meaning if saved. Share a mapper, reject unknown required financial semantics, and keep graceful fallback for informational fields such as unknown category labels/icons. Add contract fixtures. No particular new upstream enum is asserted to exist today.
7. **Make refresh gestures do real work.** BalancesScreen's `RefreshIndicator` has `onRefresh: () async {}`. Live SQLite balances are current relative to cache, not necessarily the server. Wire the gesture to the shared sync/refresh operation or remove the inactive gesture.
8. **Make checks reproducible and cover native boundaries.** CI tracks floating Flutter stable while SETUP/pubspec do not name a tested Flutter baseline. Pin a tested CI SDK and document upgrade procedure; align localization/codegen ordering with the local script. The normal CI job checks Dart only. Consider an Android build and an iOS no-codesign build on an appropriate manual/scheduled or PR workflow for native bridge/configuration changes. The Windows Android workflow is manual; it is not mandatory native PR coverage. Add focused failure/race tests from this audit, plus legacy startup migration coverage.

## Suggested work sequence and documentation maintenance

1. Fix and regression-test F1–F3 before expanding sync features. Update their documented invariants alongside code.
2. Address calendar-date storage, foreground sync ownership, transport bounds and local error recovery (F4–F7), with migration/race tests.
3. Clarify the receipt budget/usage UI and privacy wording (F8).
4. Make a documentation-only pass over the Markdown table and source-comment table. Keep historical records dated; add an “Implemented / superseded by / current behavior” note where later appendices contradict earlier summaries.
5. Add a compact current architecture document covering server-scoped identity, date/amount units, source of truth, sync delivery/lifecycle, receipt retention, resource ownership and migrations. Link it from README and decision index. Assign one canonical description to each invariant instead of copying it into multiple screens.
6. Add inexpensive repository checks for broken local Markdown links and references to removed decision files. In PR review, include changed comments/README/privacy/store copy when feature or persistence behavior changes. A link checker supplements semantic review; it cannot establish that a feature promise is true.

The existing pure calculation helpers, server-scoped category cache, injected widget dependencies, transaction-based receipt reference cleanup, in-place sync acknowledgement and detailed decision history are useful foundations. The recommended work preserves them while repairing identity, lifecycle and serialization boundaries.
